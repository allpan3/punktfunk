title: PyroWave (wired-LAN codec)
description: The wavelet codec for wired links — near-zero codec latency for a bitrate you set in bits per pixel.

PyroWave is an opt-in video codec for wired links. Every frame is a complete picture, compressed
with a wavelet transform in Vulkan compute ([upstream](https://github.com/Themaister/pyrowave)).
It encodes and decodes in a fraction of a millisecond, and pays for that with far more bandwidth
than HEVC or AV1.

Punktfunk never picks it for you. It runs when you choose it on the client and the host supports
it; otherwise the session uses the normal codecs.

## Why use it

- **Codec latency almost disappears.** Encode takes ~0.15 ms and decode ~0.07 ms at 1080p on an
  RTX 5070 Ti. Hardware HEVC takes one to several milliseconds on each side.
- **Packet loss costs one frame.** No frame depends on another: a lost frame is gone, the next
  one is whole. No keyframe request, no stutter while the stream recovers.
- **Every frame is the same size.** The network sees a steady load instead of keyframe bursts.

## Bits per pixel

PyroWave has no quality setting of its own. Its encoder fills the byte budget each frame gets,
exactly. Punktfunk sets that budget in **bits per pixel**, so one number means the same picture
at every resolution and frame rate.

The default is **1.6 bits per pixel**, the codec author's clean point: at 200 Mbps for 1080p60
he [could not spot compression artifacts](https://themaister.net/blog/2025/06/16/i-designed-my-own-ridiculously-fast-game-streaming-video-codec-pyrowave/)
without comparing side by side and zooming in.

| Mode (4:2:0, 8-bit) | At 1.6 bits/pixel |
|---|---|
| 1280×800 @ 60 (Steam Deck) | ≈ 100 Mbps |
| 1920×1080 @ 60 | ≈ 200 Mbps |
| 1920×1080 @ 120 | ≈ 400 Mbps |
| 2560×1440 @ 120 | ≈ 710 Mbps |
| 3840×2160 @ 60 | ≈ 800 Mbps |
| 3840×2160 @ 120 | ≈ 1.6 Gbps |

### Lower works, and looks softer

1.6 is a target, not a floor. PyroWave streams at any bitrate: fewer bits never break the
stream, they soften the picture.

HEVC and AV1 reuse the previous frame and send mostly what changed. PyroWave sends every frame
whole, and keeps its coding stage simple for speed, which
[costs the most at low bitrates](https://github.com/Themaister/pyrowave#trivial-entropy-coding).
When bits run short it drops fine detail first: text, thin UI lines and texture go soft, and
hard edges ring.

For scale: Steam Remote Play's PyroWave
[tops out at 500 Mbit/s](https://steamcommunity.com/groups/homestream/discussions/0/564794422009744473).
At 4K120 that is 0.5 bits per pixel, a third of the clean point.

### Why Punktfunk can carry it

A 4K120 frame at 1.6 bits per pixel is 1.66 MB, 120 times a second. The native protocol is
built for frames that size:

- **Error correction sized for big frames.** Punktfunk corrects losses in blocks of up to 4096
  packets (Reed–Solomon over GF(2¹⁶)). The GameStream protocol Moonlight speaks allows 255
  packets a block and four blocks a frame: 1,020 packets, parity included. That 1.66 MB frame
  needs more than 1,100 before any parity.
- **Paced sending.** Each frame goes out in small bursts, not all at once, so a multi-megabyte
  frame does not overrun the send buffer and stall the stream.
- **Batched packets.** `sendmmsg`/`recvmmsg` on Linux, UDP segmentation offload on Windows,
  `recvmsg_x` on macOS keep the per-packet cost small at gigabit rates.
- **Room at the top.** The host accepts up to 8 Gbps, so 2.5, 5 and 10 GbE links get used.

## Setting it up

**Host:** Linux and Windows hosts support PyroWave with nothing to install. On Linux it runs on
AMD, Intel and NVIDIA alike.

**Client:** set the video codec to **PyroWave (wired LAN)**. The option appears only on devices
whose GPU passes the decode check.

| Client | Setting | Needs |
|---|---|---|
| Linux (desktop app, controller UI, docked Deck) | Settings → Video codec | — |
| Windows | Settings → Video codec | x64 |
| Mac, iPhone, iPad, Apple TV | Settings → Codec | Apple Silicon or A13 and newer |
| Android | Settings → Video codec | 64-bit, Vulkan 1.3 GPU |

The stats overlay shows `pyrowave` as the decode path while it runs.

**Bits per pixel:** web console **Host → Settings → Video → PyroWave quality**, or
`PUNKTFUNK_PYROWAVE_BPP` in `host.env`. Any value from 0.25 to 4, from the next session. One
setting covers every client: a Deck and a 4K desktop get the same quality, each at its own
bitrate. The client's bitrate setting does not apply to PyroWave.

**Automatic fits the link.** Before the first frame the client tests the link. If it cannot
carry the rate with room to spare, the session drops to 70 % of what the link delivered, so
4K120 on Gigabit still streams, at fewer bits per pixel. The rate never rises afterwards and
the adaptive bitrate stays off; under sustained loss, switch to HEVC. To hold every session
under a fixed rate, set **PyroWave bitrate cap** (`PUNKTFUNK_PYROWAVE_MAX_MBPS`).

## 4:4:4 and HDR

Both follow the client's settings, as with HEVC and AV1, and scale from your bits per pixel:

- **4:4:4** (full chroma, sharp coloured text): ×1.625, so 2.6 at the default. Chroma
  compresses better than luma, so it costs less than the 2× its extra samples imply.
- **10-bit and HDR** (BT.2020 PQ): +15 %. On Linux, HDR needs a `punktfunk-gamescope` output
  ([the HDR chain](/docs/hdr#per-host)).

Together, 4:4:4 HDR at the default is ~3.0 bits per pixel.

## Checking a Linux host is zero-copy

The host logs which capture path a session took, once:

```
capture pipeline resolved: dmabuf-passthrough → pyrowave
```

`dmabuf-passthrough` is zero-copy. `cpu` means every frame is copied, which lowers the frame-rate
ceiling and raises CPU use; the next line names the cause, such as `PUNKTFUNK_ZEROCOPY=0` or a
compositor that would not hand over a dmabuf.

## Limits

- Wired links only. Wi-Fi cannot carry these rates; use HEVC or AV1 there.
- No decoder in the Windows ARM64 client or the 32-bit Android build.
